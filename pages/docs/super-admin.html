Super-Admin manual

You are the root of the trust tree. You configure providers, security, penalties, and create sub-admins with scoped permissions. Every action is auditable.

Overview

A super-admin can do everything: enable/disable P2P providers, edit the security policy, create or revoke sub-admins, issue penalties, and rewrite system config. Sub-admins receive a permission allow-list and cannot create other admins.

  • All write actions are logged to audit_log.
  • All configuration is stored in versioned JSON files: config.json, p2p-providers.json, security.json, penalties.json, ecosystem-currencies.json.
  • All passwords are bcrypt-hashed (cost is set in security.json > auth.bcrypt_cost).

First run & password

On the first request to any backend page, b30_ensure_super_admin() reads config.json > super_admin and creates the super-admin row in admins if none exists.

{
  "super_admin": {
    "email":     "superadmin@2030b.local",
    "password":  "change-me-now",
    "full_name": "2030B Super Admin"
  }
}

After first sign-in, change the password from the Admins tab. The original super_admin.password in JSON is only used for seeding — the live bcrypt hash lives in the SQLite admins table.

Manage sub-admins

Open the Admins tab → New sub-admin. Provide email, full name, password, and check the permissions you want to grant.

  1. Pick a strong password (at least security.json > auth.password_min_length chars).
  2. Grant only the permissions they need (least-privilege).
  3. Use the toggle to disable a leaver — preserves audit trail.
  4. Deleting an admin is permanent but does not delete their audit log entries.

P2P providers

The whole platform is provider-agnostic. Open the P2P providers tab to enable a new exchange — every system page (wizard, op modal, admin lists, dashboards, docs) re-renders automatically.

Per-provider fields

  • code — short ID (lowercase). Used as platform in DB rows.
  • enabled — boolean. Disabled providers stay in the DB but vanish from UI.
  • name_{lang} — translated name (12 languages).
  • color_primary / color_accent — used by the logo renderer.
  • min_usdt_buy / min_usdt_sell / max_usdt_per_op — enforced server-side.
  • level_required — minimum user level allowed to use this provider.
  • fee_buy_percent / fee_sell_percent — added/subtracted from credit math.
  • supported_fiat — array of ISO-4217 codes.
  • uid_label_{lang} / uid_regex / uid_hint_en — UI for capturing the user's exchange UID.

Click Save providers after editing. The change persists locally first (so you can preview), then is written to p2p-providers.json by the PHP backend (POST ?op=admin.providers.save).

Security policy

The Security tab edits security.json. Each block is enforced both client-side (UX warnings, file size, etc.) and server-side (PHP bootstrap reads the same file).

auth — bcrypt cost, password min length, 2FA, session TTL.
rate_limits — per-minute caps for signin/signup/admin/api.
csrf / cors / csp — request hardening & cross-origin.
upload — MIME allow-list, max size, EXIF strip, p-hash dup check.
ip_policy — block Tor, warn VPN, country block/allow.
fraud_detection — duplicate screenshot, max ops/day, strikes.
audit — what to log, retention days.
data_privacy — GDPR export / delete / anonymize.

Penalties

Rules live in penalties.json. Each rule has a code, severity, default credits_delta, and an optional appeal window. Issued penalties are stored in the penalties table and (if negative) automatically debit the user's credits.

Workflow

  1. Admin sees a fake pairing → opens Penalties tab → New penalty.
  2. Pick the rule (autofills severity + credits_delta).
  3. Add evidence (tx_id, pairing_id) and a reason.
  4. User can appeal — status becomes appealed; a super-admin can Revert to refund credits.

Ecosystem currencies

Each project (e.g. CTC, GTC, …) has a credit-to-currency rate. Edit rates from the Ecosystem tab. A user's total_credits can be redeemed against any project's currency at the current rate.

Audit log

Every privileged action writes a row to audit_log with actor, action, target, notes, and timestamp. Retrieve the latest via GET ?op=admin.audit&limit=100. Retention is configured in security.json > audit.retention_days.
